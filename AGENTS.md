# AGENTS.md — интернет-магазин подшипников «ЭВЕРЕСТ»

## Цель проекта

Создать производственный B2B-каталог подшипников и промышленных комплектующих для ООО «ЭВЕРЕСТ».

Сайт должен помогать закупщикам и инженерам:

- находить подшипники по ГОСТ, ISO, обозначению и размерам;
- сравнивать характеристики;
- видеть проверенные соответствия и ограничения аналогов;
- собирать несколько позиций в заявку;
- отправлять спецификацию менеджеру;
- создавать сделку в Bitrix24 без использования лидов.

Это не обычный розничный магазин. На первом этапе публичные цены, онлайн-оплата и автоматическое подтверждение наличия не используются.

## Репозиторий

Репозиторий ранее использовался для Python-скрипта очистки дублей Bitrix24. Перед перестройкой:

1. Проведи аудит текущих файлов.
2. Не удаляй старый рабочий код без сохранения истории Git.
3. Зафиксируй список удаляемых или переносимых файлов в `docs/migration-from-legacy.md`.
4. После аудита разрешается заменить содержимое основной ветки новым web-проектом, если это прямо указано в текущей задаче.
5. Секреты, webhook, токены и `.env` не коммитить.

## Технологический стек

Использовать актуальные совместимые стабильные версии:

- Next.js App Router;
- TypeScript strict;
- Tailwind CSS;
- shadcn/ui или Radix UI;
- PostgreSQL;
- Prisma;
- Zod;
- React Hook Form;
- Vitest;
- Playwright;
- Docker для production-развёртывания.

На первом этапе каталог может работать на типизированных mock-данных через интерфейс репозитория. Не привязывать UI напрямую к JSON.

## Бренд и визуальный стиль

Стиль: премиальный промышленный B2B, инженерный, спокойный, функциональный.

Цвета:

- Graphite Black: `#111111`;
- Warm White: `#F6F5F3`;
- Steel Gray: `#C8C8C8`;
- Signal Orange: `#F26A21`;
- Industrial Navy: `#223448`.

Шрифты:

- Inter или Hanken Grotesk — интерфейс;
- Roboto Mono — обозначения, размеры, характеристики.

Не использовать:

- визуальный шум;
- неон;
- случайные фотографии офисных сотрудников;
- неподтверждённые отзывы;
- вымышленные сертификаты;
- фразы «лучшие цены», «всё в наличии», «официальный дилер» без доказательств;
- чужие логотипы, тексты и изображения из референсов.

## Основные страницы

- `/` — главная;
- `/catalog` — каталог;
- `/search` — результаты поиска;

- `/selection` — подбор по параметрам;
- `/brands` — бренды;
- `/knowledge` — база знаний;
- `/about` — о компании;
- `/delivery` — доставка и оплата;
- `/contacts` — контакты;
- `/request` — корзина-заявка.

## Каталог

Основные поля товара:

- наименование;
- артикул;
- ГОСТ;
- ISO;
- альтернативные обозначения;
- бренд;
- страна;
- тип;
- `d`, `D`, `B/H`;
- масса;
- зазор;
- класс точности;
- уплотнение;
- сепаратор;
- материал;
- грузоподъёмность;
- предельная частота вращения;
- температурный диапазон;
- статус поставки;
- ориентировочный срок;
- технические документы.

Поиск должен учитывать регистр, пробелы, дефисы, `/`, варианты суффиксов и распространённые соответствия ГОСТ/ISO.

## Аналоги

Использовать статусы:

- `DIRECT`;
- `ONE-WAY`;
- `PARTIAL`;
- `SIZE ONLY`;
- `NO DIRECT`;
- `CONFLICT`.

Уровни доказательности:

- `A`;
- `B`;
- `C`;
- `R`.

Запрещено объявлять подшипники прямыми аналогами только по совпадению размеров.

## Bitrix24

- Лиды не использовать.
- Заявка должна создавать или связывать компанию, контакт и сделку.
- Интеграция только на сервере.
- По умолчанию `mock` или `read-only`.
- Запись разрешается только через отдельный флаг и серверные переменные окружения.
- ID пользовательских полей хранить в серверной конфигурации, а не в компонентах.
- Никогда не выводить webhook или токен в клиент, Git, логи и отчёты.

## Правила разработки

- TypeScript strict, без необоснованного `any`.
- Mobile-first, диапазон 360–1920 px.
- Семантическая HTML-разметка.
- Доступность с клавиатуры.
- Поддержка `prefers-reduced-motion`.
- Серверная валидация форм.
- Состояния loading, empty и error обязательны.
- После каждого этапа запускать `lint`, `typecheck`, тесты и production build.
- Не изменять несвязанные части проекта.
- Не маскировать ошибки отключением правил линтера или тестов.
- Архитектурные решения фиксировать в `docs/decisions.md`.
- В конце каждой задачи перечислять изменённые файлы, проверки и известные ограничения.
