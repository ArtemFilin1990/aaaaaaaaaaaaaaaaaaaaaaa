# Корзина-заявка

## Сценарий

1. Пользователь добавляет товар из каталога или карточки.
2. Позиция сохраняется в браузерном черновике.
3. Пользователь указывает количество, единицу, требуемый срок и допустимость аналога.
4. Заполняются данные компании, ИНН, контакт, город и способ связи.
5. Клиент и сервер независимо валидируют данные через Zod.
6. Сервер принимает запрос только через `POST /api/request`.
7. На текущем этапе адаптер возвращает номер `MOCK-*` и не выполняет внешние запросы.
8. Корзина очищается только после подтверждённого ответа сервера.

## Черновик

Ключ `everest-commercial-request-v1` хранится в `localStorage`. В нём нет токенов и webhook, но могут находиться введённые пользователем контактные данные. Перед production необходимо утвердить срок хранения, текст политики и механизм явной очистки.

## Идемпотентность

Каждый черновик получает UUID `idempotencyKey`. Повторная отправка одного ключа в пределах жизни серверного процесса возвращает тот же mock-номер и признак `duplicate=true`.

Текущий in-memory реестр не является production-хранилищем. Для production ключи должны сохраняться в PostgreSQL или другом общем хранилище с ограниченным сроком жизни.

## Bitrix24

Реальная запись заблокирована. Адаптер доступен только при:

- `B24_MODE=mock`;
- `B24_WRITE_ENABLED=false`.

При любых других настройках endpoint возвращает 503. Реальный адаптер будет отдельным этапом и должен:

- найти компанию по ИНН;
- найти контакт по телефону/e-mail;
- не создавать лид;
- создать или связать компанию и контакт;
- создать сделку;
- передать позиции, количество, сроки, допустимость аналога и источник заявки;
- исключить повторную запись по idempotency key.

## Что ещё требуется перед production

- rate limiting;
- honeypot или CAPTCHA по результатам оценки спама;
- проверка и хранение вложений;
- юридически утверждённая политика обработки данных;
- серверное долговременное хранение idempotency key;
- маскирование персональных данных в логах;
- мониторинг ошибок доставки в CRM.
