# Разработка сайта в режиме «Работа»

Этот документ задаёт обязательный порядок работы AI-агента в мобильном режиме «Работа».

## 1. Источник истины

Перед каждой задачей агент обязан прочитать:

1. `AGENTS.md`;
2. `README.md`;
3. документы в `docs`, относящиеся к задаче;
4. активное задание из `tasks`.

Текущий код и история Git важнее текста предыдущих ответов в чате.

## 2. Рабочий цикл

Каждая задача выполняется отдельным этапом:

1. проверить ветку, HEAD и `git status`;
2. изучить существующий код;
3. сформулировать короткий план;
4. выполнить изменения;
5. запустить относящиеся к задаче проверки;
6. исправить найденные ошибки;
7. создать атомарные локальные коммиты;
8. опубликовать ветку и создать Pull Request, если GitHub-аутентификация доступна;
9. при отсутствии аутентификации экспортировать коммиты и рабочее состояние.

Агент не должен останавливаться после анализа, если выполнение технически возможно.

## 3. Git

- `main` напрямую не изменять из режима «Работа».
- Для каждого этапа использовать отдельную ветку `codex/<task-name>`.
- Force push запрещён.
- Историю не переписывать.
- Не удалять архивную ветку старого проекта.
- Перед началом задачи получить актуальный `main`.
- Не продолжать работу поверх чужих незакоммиченных изменений.
- Один логический блок изменений — один атомарный коммит.

## 4. Если GitHub недоступен

Отсутствие `gh` не блокирует разработку и локальные коммиты, но блокирует подтверждённую публикацию.

Агент обязан:

1. сохранить локальные коммиты;
2. не утверждать, что push или Pull Request выполнены;
3. создать каталог `export` вне репозитория;
4. выполнить `git format-patch` от удалённого базового коммита до текущего HEAD;
5. создать архив только из `git ls-files`;
6. исключить `.env`, `.git`, `node_modules`, `.next`, отчёты, кеши и логи;
7. создать `EXPORT_MANIFEST.md` с базовым SHA, итоговым SHA, списком коммитов и результатами проверок;
8. прикрепить patch-файлы и архив к ответу.

После экспорта не удалять рабочий репозиторий.

## 5. Проверки

Минимум после каждого этапа:

```bash
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Дополнительно, когда применимо:

```bash
pnpm exec prisma format
pnpm exec prisma validate
pnpm test:e2e
```

Если PostgreSQL или Docker недоступны, это фиксируется как ограничение. Проверку нельзя помечать успешной, если команда фактически не выполнялась.

## 6. Секреты

Запрещено добавлять в Git:

- `.env` и `.env.local`;
- Bitrix24 webhook;
- API-ключи;
- пароли баз данных, кроме явно демонстрационных локальных значений в `.env.example`;
- персональные данные клиентов;
- логи с токенами и полными URL webhook.

Интеграции Bitrix24 и 1С по умолчанию работают только в mock-режиме.

## 7. Отчёт по задаче

Финальный ответ должен содержать:

- ветку;
- исходный и итоговый SHA;
- список коммитов;
- изменённые области;
- выполненные команды и их фактический результат;
- ссылку на Pull Request или прямое указание, что публикация не выполнена;
- известные ограничения;
- следующий этап.

## 8. Последовательность разработки

1. Стабилизация каркаса и CI.
2. Каноническая Prisma-модель каталога.
3. Нормализация и поиск ГОСТ/ISO.
4. Каталог и фильтры.
5. Карточка товара и безопасные аналоги.
6. Корзина-заявка.
7. Серверная интеграция Bitrix24.
8. Импорт XLSX/CSV и подготовка 1С.
9. Главная страница и дизайн-система.
10. SEO, аналитика и база знаний.
11. Полный E2E-аудит.
12. Production-развёртывание.

Сложный дизайн и анимации не должны опережать работающее ядро каталога.
